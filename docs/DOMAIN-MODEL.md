# Domain model & schema decisions

## Base types

| Type | Purpose |
| --- | --- |
| `Entity` | Guid identity + value equality. Ids are generated by the application (`Guid.NewGuid()`), so inserts are batchable and sharding-friendly. |
| `GlobalEntity` | Adds audit + soft delete for cross-tenant rows (`User`, `Tenant`, `Permission`, tokens). |
| `TenantEntity` | Adds `TenantId`, audit, soft delete and concurrency for every center-owned row. |

`Money` is an EF **owned type**; each owner gets `{Property}_Amount decimal(18,2)` and `{Property}_Currency char(3)`.

## Tenancy & isolation

`AppDbContext.ApplyGlobalQueryFilters` reflects over the model and attaches
`!e.IsDeleted && e.TenantId == CurrentTenantId` to every relevant entity. `CurrentTenantId`
comes from `ITenantContext` (JWT claim → header → subdomain), so EF parameterises it and the
same compiled query is safe across tenants. The audit interceptor refuses to let a new row
carry `Guid.Empty` as its tenant.

Unique constraints include `TenantId` and are filtered on `IsDeleted = false`, so re-creating a
soft-deleted row (e.g. re-enrolling a student) does not collide with history.

## Concurrency

Every `TenantEntity` carries a `byte[] RowVersion` mapped as an EF concurrency token with
`ValueGeneratedNever`. `AuditInterceptor` rotates it on insert/update, so EF places the
original value in the `WHERE` clause and the fresh value in `SET`. A
`DbUpdateConcurrencyException` bubbles up as a 409 conflict at the API boundary.

## Key aggregate boundaries

- **Tenant** is the root; nothing tenant-scoped can exist without it.
- **User** is global; `TenantMembership` + `UserRole` attach it to centers. A teacher can also be a parent in another center.
- **Course → Subject → Topic** is the curriculum tree. **Batch** snapshots a course into a time-bound cohort; `SyllabusVersion` and `BatchTopic` let two cohorts run different syllabus revisions.
- **ScheduleRule** holds recurrence; **ClassSession** rows are materialised instances. Attendance attaches to instances, never to rules — cancellations and make-up classes stay explicit.
- **AssessmentAttempt → StudentAnswer** records attempts; **GradeEntry** is a denormalised, query-friendly gradebook projection used by reports and rank calculations.
- **Invoice → InvoiceLine / Payment** and **LedgerEntry** keep finance auditable. Ledger rows are append-only; refunds are separate rows, never mutations of a payment.
- **OutboxMessage** is written in the same transaction as the business change. A worker (Hangfire/Quartz or a polling background service) dispatches notifications, ledger postings and search indexing from it.

## Scale-out notes

- API is stateless; run N replicas behind a load balancer. SignalR needs a Redis backplane once more than one replica is used.
- Read-heavy dashboards should read from CQRS projections, not these write tables.
- Heavy reports, attendance roll-ups and fee generation belong in Hangfire/Quartz jobs fed by the outbox, not in request threads.
- Partition candidates once a single tenant gets huge: `AuditLog`, `Notification`, `OutboxMessage` by `TenantId`/time; `ClassSession` by `TenantId` + date range.


## Application & background layers

- **Application** owns use cases as MediatR slices. It depends only on the Domain and on small
  interfaces (`IApplicationDbContext`, `ICurrentUser`, `ITokenGenerator`, `IPasswordHasher`) —
  never on EF Core or ASP.NET Core directly.
- **TenantGuardBehavior** refuses `IRequiresTenant` commands when `TenantId` is empty; global
  query filters then scope every read. Login deliberately calls `IgnoreQueryFilters()` on the
  small identity tables it must search globally before a tenant is known.
- **Outbox pattern**: a command writes the business row and the `OutboxMessage` in one
  transaction. Hangfire drains it in batches of 50; handlers create notifications, and the
  `ProcessedAt` stamp is saved in the same unit of work. Failures increment `RetryCount`.
- **Transactional boundaries**: invoice creation computes `Money` totals in the domain value
  object; payment recording updates the invoice, inserts the payment, posts two ledger rows
  and queues the event in a single `SaveChangesAsync`.
